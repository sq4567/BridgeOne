# BridgeOne 리팩토링 스킬

## 핵심 원칙

**리팩토링 = 외부 동작은 그대로, 내부 구조만 개선.** 동작이 달라지면 그건 리팩토링이 아니라 기능 변경이다.

### 범위 결정 기준

코드베이스 전체를 보지 않는다. 이번 Phase에서 추가하거나 수정한 파일을 기점으로 출발한 다음, 아래 기준으로 연관 파일 포함 여부를 판단한다.

**포함**: 새 기능 때문에 구조가 직접 엉킨 연관 파일 (예: 새 상수를 만들면서 기존 상수 파일과 중복이 생긴 경우)

**제외**: 원래부터 지저분했던 무관한 파일, 이번 변경과 이유가 다른 파일

판단이 애매하면 유저에게 확인을 구한다.

---

## 발동 후 흐름

1. **파일 식별** — 이번에 수정/추가한 파일 목록 확인 (git status 또는 유저에게 직접 물어봄)
2. **연관 파일 판단** — 같은 이유로 함께 정리돼야 할 파일이 있으면 범위에 추가
3. **진단** — 대상 파일 읽고 아래 유형 기준으로 실제로 존재하는 문제 파악. **없으면 "정리할 게 없다"고 보고하고 종료**
4. **제안** — 발견한 문제와 수정 방향을 먼저 제시, 유저 동의 후 진행
5. **실행** — 진단된 항목만 수정. 요청 범위를 벗어난 개선·주석 추가·추상화 레이어 금지
6. **빌드** — `.\gradlew assembleDebug` (프로젝트 루트 `src/android/`에서 실행)

## 다루는 리팩토링 유형

### 1. 중복 제거

동일하거나 거의 같은 코드 블록이 2개 이상 반복될 때, 단일 함수나 확장 함수로 통합한다.

BridgeOne에서 자주 나타나는 패턴:
- `TouchpadWrapper.kt` 내 여러 제스처 핸들러에 반복되는 햅틱 호출 블록
- 여러 Composable에서 동일한 조건부 로직 반복

통합 전 확인할 것: 겉보기엔 비슷해도 미묘한 파라미터 차이가 있으면 무리하게 합치지 않는다.

### 2. 파일/함수 분리

Composable이나 함수가 너무 많은 책임을 지고 있을 때 응집도 높은 단위로 추출한다.

BridgeOne 판단 기준:
- 단일 `.kt` 파일이 500줄 이상으로 비대해진 경우
- 한 Composable이 UI 렌더링 + 제스처 처리 + 상태 계산 + 통신을 동시에 담당하는 경우
- 특정 기능(예: 관성 스크롤, 엣지 존 판정)이 독립적으로 테스트되거나 재사용될 가능성이 있는 경우

자주 분리 대상이 되는 파일: `TouchpadWrapper.kt`, `StandardModePage.kt`, `EssentialModePage.kt`

분리 후 public API가 달라지면 유저에게 알린다.

### 3. 상수 정리

구현 도중 임시로 하드코딩한 값, 또는 파일 내부에 흩어진 조정 가능한 값을 `ui/common/*Constants.kt`로 이동한다.

기존 상수 파일 (추가할 위치 판단 기준):
- `ScrollConstants.kt` — 스크롤, 관성, 가이드라인 관련
- `PointerDynamicsConstants.kt` — 커서 이동 속도, 가속도 관련
- `LayoutConstants.kt` — 패딩, Safe Zone, 크기 관련
- `MacroConstants.kt` — 매크로 관련

**상수 기본값 주석 정책 준수** (CLAUDE.md 전역 규칙):
```kotlin
/** 설명. 기본값: 8f */
const val EXAMPLE_THRESHOLD_DP = 8f

/** 설명. 기본값: 800f ⚠️ 의도적 변경 */
const val EXAMPLE_TIME_CONSTANT_MS = 1500f
```

HID 키 코드, 색상 상수, 로그 태그처럼 고정된 식별자 성격의 값은 `*Constants.kt` 이동 대상이 아니다.

## 프로젝트 규칙 요약

- 수정 전 반드시 파일 읽기
- 진단된 문제만 손댐 — 주변 코드 "정리", 불필요한 error handling·추상화 레이어 추가 금지
- 빌드 에러는 즉시 수정. 에러가 없어질 때까지 빌드-수정 반복
- 빌드 경고는 수정하지 않더라도 유저에게 보고
